7. Resource title, identity and role correlation

================================================

ResourceIntentAuthority.live_view() copies identity.normalised_title[:240] into display_title (resource_intent.py:1328-1341). Human-readable text is therefore usable when supplied. It is normalized and potentially truncated; availability does not establish exact video-title fidelity. No browser sensing was widened, and no example titles were fabricated or searched as acceptance criteria.

The composite control_view includes session_id, foreground, resource_intent and study_app_category. Its metadata exposes source_observation (ResourceObservation), observation_sequence, observed_monotonic_ns, resource_key, study_context_token and observation_token. The existing consumer validates same-sample identity/coherence (view.py:1036-1088). A future observer can preserve this already-public evidence without reading private authority state. A mismatched or unavailable metadata bundle cannot be assigned factual RI event time.

Read PRIMARY/LATER from durable study_resources, using session_id + study_block_id + study_generation + resource_key and identity kind/version where relevant. StudySnapshot supplies block_id, generation and context_token. SECANT scope.context_id is constructed as str(session_id) + ":" + study.context_token (monitor.py:2640); scope.target_resource_id is the PRIMARY resource key. Prefer exact context/token matching rather than heuristic title or proximity matching.

Existing read_study_resources(session_id=..., study_block_id=...) returns immutable StudyResourceFact values and orders by qualified_monotonic_ns, resource_fact_id (storage.py:2847-2866). It does not filter generation; a caller must enforce exact generation itself. The persistence writer uses immutable fact IDs and rejects conflicting retries (storage.py:1251-1271). Pending runtime resources are not proof of a durable commit.

Snapshot findings: 11 qualified BROWSER records across 9 session/block/generation scopes; 9 PRIMARY, 2 LATER. No DESKTOP qualification rows in this snapshot. All provenance JSON keys observed: classification, effective_state, observation_id. This does not supply explicit confirmation_source or a full resource-visit order.

The role describes authoritative qualification. A display may say PRIMARY or LATER, but "first visit" or "2nd resource" would add unsupported semantics. A chronological rank of qualified records would need to be explicitly labeled as such and is not an existing authoritative ordinal.

11. Smallest future non-organ implementation allowlist

======================================================

Recommendation only; nothing implemented. For recording the proven subset, the candidate allowlist is PERSISTENCE/schema.py (a separately reviewed additive persistence contract), PERSISTENCE/storage.py (existing serialized writer ownership), one new passive recorder module, and CONTROL_STATION/launcher.py for subscription/lifetime wiring.

Launcher seam is concretely present: startup_completed(exit_code, window) receives ControlStationWindow at launcher.py:109-118; window.engine is created at application.py:14902. The recorder can subscribe there before user-driven monitoring begins and seed current_session_id() (controller.py:363). Because the current launcher has no recorder subscription, this external composition seam is necessary within the restricted allowlist. A future implementation must retain recorder lifetime and address orderly flushes; neither is implemented or runtime-tested here.

The allowlist cannot recover a missing raw fact contract, historical data already lost, or an original UTC stamp absent from the public SECANT fact. Do not widen it to controller.py, application.py or any organ. A recorder using only these seams must advertise its bounded observation coverage and missing-data cases.

Before an actual database change: preserve a consistent backup including any active WAL state, review the exact intended schema/data diff, validate migration and rollback on a disposable copy, and recheck integrity and declared FKs. The snapshot kept for this audit is evidence, not a claim that a future live database has been backed up.
